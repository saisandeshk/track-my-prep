# Systems and ML Systems resource audit

Audited 2026-07-26 from the saved-tab catalogue. “Primary” means a resource worth following sequentially; “supplement” fills a deliberate gap; “reference” is consulted while building/debugging. Access means access to the public materials observed, not enrolment credit. Effort is an estimate except where the provider states a duration.

## Bottom line

The collection is unusually deep in ML systems/GPU work, but breadth is not a reason to run several full courses at once. A defensible preparation spine is:

1. **Practical software and system-design base:** one language, Git, SQL/API/networking basics, then **HLD Handbook** plus timed designs.
2. **System internals:** one OS course and enough databases/distributed systems to explain failure, storage, concurrency and trade-offs.
3. **ML system design:** production ML lifecycle and one product-design practice loop (data/labels/features, training, serving, evaluation, feedback, cost/safety).
4. **ML systems implementation:** Deep Learning Systems, then one modern course for training/inference systems.
5. **GPU/kernel specialization:** a parallel/GPU foundation followed by _one_ kernel path; use vendor docs while implementing and profiling.

That order keeps interview HLD/LLD competence independent from ML specialization and avoids mistaking accelerator optimization for general system-design preparation.

### HLD and LLD are distinct deliverables

- **HLD:** use the HLD Handbook and 8–12 timed designs (URL shortener, chat, feed, file store, payments, rate limiter, metrics pipeline, recommendation/LLM service). Produce one-page diagrams and explicit trade-offs.
- **LLD:** use the AlgoMaster LLD material if available, but build 4–6 small designs in one language: cache with eviction, task scheduler, parking/booking, notification service, logging/metrics SDK, payment workflow. Require tests, interfaces, error states, thread-safety where relevant, and a short README. There is no independent, fully verified LLD course in the listed groups that should displace this code-first practice.

## Recommended concept paths

### A. Software/system-design interview path (12–16 weeks part-time)

1. Language fluency, testing, Git, HTTP/REST, SQL and basic networking; implement a thread-safe cache and a small API.
2. HLD Handbook foundations/building blocks; write two designs weekly and revise them after identifying a failure mode.
3. One systems depth lane: CS162 _or_ selected 15-445 modules (storage/indexes/transactions). Add distributed-systems papers/labs only after the basics.
4. LLD coding portfolio and interview drills (AlgoMaster optional). The output is executable, reviewed code—not UML alone.

### B. ML system-design path (8–12 weeks after ML basics)

1. MLSysBook: lifecycle, data/feature quality, training/evaluation, serving, monitoring, reliability and cost.
2. Design and implement a batch-to-online project: dataset/versioning, reproducible training, offline metrics, service API, logging/drift checks, rollback and a dashboard/readme.
3. Do four case studies: retrieval/ranking, recommendation/feed, streaming fraud/anomaly, and LLM/RAG service. For each state data contracts, target metric, latency/throughput/SLO, evaluation, feedback loop, abuse/safety, and cost.
4. Use AlgoMaster’s ML System Design only as timed question practice; verify decisions against the build.

### C. ML systems / AI-infra path (16–24 weeks part-time)

1. DLsys core (autodiff/tensor library) → CMU ML Systems _or_ UCSD 291.
2. Pick **one** specialization: CMU LLM Systems (serving/training) or MIT EfficientML (compression/edge); use 15-779 readings selectively.
3. Build one reproducible serving system and one training/infra project. The AI-infra curriculum is the practical platform complement; scope cloud spending before its labs.

### D. GPU-kernel path (only after C or equivalent)

1. CS149/15-418 concepts + NVIDIA’s eight-hour Python syllabus.
2. Modern GPU Programming for MLSys; implement, test and profile a GEMM and attention-related kernel.
3. Use CuTe/cuTile/TileLang only when a project dictates the tool; consult glossary/resource list as references.

## Placement-data reality check (aggregate only)

I inspected the CSV **schema and aggregate public-role text only**, without reproducing names, employers, compensation, applications, identifiers or other personal/private fields. `placement_jobs.csv` parsed as 471 records and its titles/skills/descriptions contained: Python in 115, SQL in 28, ML/AI/GenAI/LLM terms in 91, and systems/distributed/cloud/backend terms in 49. This is a noisy keyword signal—not a labour-market study and not a taxonomy source. It supports keeping Python, production engineering, ML fundamentals and systems communication visible in every path; it does **not** justify collapsing general software/HLD, MLOps, ML system design and GPU-kernel roles into one preparation track.

## Explicit overlap and access decisions

- Choose one each: **CS149/15-418**, **CMU 15-442/642/UCSD 291**, and **CMU LLM Systems/MIT EfficientML**. Their topic lists overlap enough that parallel completion usually lowers project depth.
- HLD Handbook is the open primary for general HLD; AlgoMaster is optional/gated-aware interview practice. Build Distributed System is account-gated for active practice, so it is not assumed available.
- NVIDIA documentation, Modal glossary, Wafer list, TileLang, CuTe and cuTile are valuable references but should not be counted as independent courses.
- Maintain one public portfolio artifact per path: design doc + implementation + tests + benchmark/operational evidence. This is the missing connective tissue across otherwise excellent reading material.
